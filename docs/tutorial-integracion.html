Si usas Windows, empieza por aquí

make no existe en Windows y los .sh necesitan bash, así que en cmd fallan antes de hacer nada. Hay un atajo equivalente que no depende de ninguno de los dos.

Usa pg en lugar de make

Todo el trabajo ocurre dentro de los contenedores, así que sólo hacía falta una forma de lanzarlo desde Windows. pg.cmd está en la raíz del repositorio y hace exactamente lo mismo.

REM en cmd.exe
> pg              REM la lista de comandos
> pg dev          REM = make dev

# en PowerShell: el .\ es obligatorio
PS> .\pg dev
PS> .\pg doctor
PS> .\pg logs worker
«El término 'pg' no se reconoce» Estás en PowerShell, que no ejecuta programas del directorio actual salvo que se lo pidas con .\ — es una medida de seguridad, para que un fichero suelto en una carpeta no suplante a un comando del sistema. cmd.exe sí los ejecuta. Escribe .\pg dev y funciona igual.
En Linux / macOSEn Windows
make devpg dev
make doctorpg doctor
make smokepg smoke
make almacenpg almacen
make probar-formulariopg formulario
make dev-rutaspg rutas
make dev-resetpg reset
La alternativa Si prefieres los comandos originales, Git para Windows trae Git Bash y ahí make y los .sh funcionan tal cual. Las dos vías son válidas; pg evita instalar nada.

Dos trampas de curl en Windows

Windows 10 y 11 traen curl, pero -s silencia también los errores: si el servicio no responde, no imprime nada y parece que el comando ha ido bien. Usa -i, que enseña el estado.

REM engañoso: si falla, no dice nada
> curl -s http://localhost:8000/health

REM así se ve lo que pasa
> curl -i http://localhost:8000/health

En PowerShell, curl es un alias de Invoke-WebRequest y no acepta las mismas opciones. Usa curl.exe con el .exe explícito, o mejor: pg doctor, que no necesita ninguna de las dos.

Qué habla con qué

Antes de tocar nada, conviene tener claras las cuatro piezas y por dónde se pasan la pelota. Casi todos los fallos de integración son una de estas flechas que no llega.

1 · Navegador

El shortcode [crear_proyecto_v6] arma un JSON y lo manda a WordPress con el nonce de la sesión.

2 · WordPress

Traduce ese JSON al contrato del motor, resuelve la ubicación a código INE y firma la petición con HMAC.

3 · Motor

Encola el cálculo, lo hace en segundo plano y guarda el informe.

4 · Callback

El motor avisa a WordPress, firmando también. WordPress publica el proyecto.

La flecha 4 es la que más se rompe, y siempre por lo mismo: el motor tiene que poder alcanzar WordPress por su nombre de red. Dentro del contenedor del motor, localhost es el motor, no WordPress.

Regla del tutorial Todo esto se hace en local. No se toca powergis.es hasta la etapa 7, y ahí se toca una copia. El circuito nuevo cambia cómo se crean los proyectos: probarlo en producción es probar sobre clientes.

Levantar el entorno Etapa 1

Un solo comando arranca motor, base de datos, cola, worker y un WordPress limpio con el plugin ya activo.

Arrancar

Necesitas Docker y el repositorio descomprimido. Nada más: Python, PHP y PostgreSQL van dentro de los contenedores.

$ cd powergis
$ make dev

Tarda un par de minutos la primera vez porque construye la imagen del motor. Al terminar imprime las tres direcciones.

Deberías ver WordPress http://localhost:8080 con los usuarios admin/admin y cliente/cliente, y el motor en http://localhost:8000/docs.

Comprobar que las piezas están en pie

$ make dev            # pg dev  en Windows
$ make setup          # pg setup — instala WordPress

Y en cuanto arranque, antes que nada:

$ make doctor         # pg doctor

Comprueba desde dentro del contenedor —así que funciona igual en Windows— PostgreSQL, el catálogo, las geografías, los municipios, el almacén, Redis y si hay algún worker vivo. Cada fallo viene con el comando que lo arregla.

Deberías ver api, worker, postgres, redis, wordpress y mariadb en marcha, y el doctor avisando de que el almacén está vacío. Eso último es normal todavía: lo llenas en la etapa 3.
Corregido: el fallo que tumbaba los dos Si vienes de una copia anterior a esta, verás SettingsError: error parsing value for field "allowed_origins". pydantic-settings intentaba interpretar como JSON el valor ALLOWED_ORIGINS=http://localhost:8080, y el error saltaba al IMPORTAR la configuración: se llevaba por delante a la API y al worker a la vez. La API caída con curl -s no imprime nada, así que parecía un problema sólo del worker. Ya acepta lista con comas y array JSON, y hay ocho pruebas que cargan la configuración desde el entorno.
Si el worker sale «Restarting» Es el único servicio que no puede fallar en silencio: sin él, los informes se encolan y no los calcula nadie. El contenedor se reinicia en bucle, así que docker compose ps sólo dice que está reiniciando, no por qué. Los logos están en: docker compose -f docker-compose.dev.yml logs worker (o pg logs worker). Mira las últimas 20 líneas antes del reinicio: ahí está la causa real.
Puertos ocupados El entorno usa 8080, 8000, 5433 y 6380. Los dos últimos van desplazados a propósito para no chocar con un PostgreSQL o un Redis que ya tengas. Si docker compose ps muestra puertos sin publicar, casi siempre es que ya había algo escuchando.

El motor solo, sin WordPress Etapa 2

Antes de conectar nada, comprueba que el motor funciona por su cuenta. Si esto falla, no tiene sentido mirar WordPress.

Prueba de humo

Firma y llama al motor igual que haría WordPress. Comprueba también lo que no debe pasar: que una lectura sin firma se rechace.

$ make smoke          # pg smoke  en Windows

Corre dentro del contenedor, en Python, sin bash ni openssl: por eso funciona igual en los tres sistemas. (La versión en bash sigue ahí como make smoke-bash, para quien la prefiera en Linux o macOS.)

Deberías ver Cinco comprobaciones en verde, incluida «una lectura sin firma se rechaza» y «el informe básico no trae datos de las secciones de pago».
Si sale 401 invalid_signature El secreto del motor y el de WordPress no coinciden. En local los dos valen dev-secreto-compartido-cambialo-en-produccion-0123456789: está en docker-compose.dev.yml, en el entorno del motor y en WORDPRESS_CONFIG_EXTRA. Tienen que ser idénticos, carácter a carácter.

Meter datos Etapa 3

El almacén arranca vacío. Hay dos caminos y conviene hacerlos en este orden: primero datos falsos para probar la fontanería, luego los del INE.

Primero: datos sintéticos

Sirven para comprobar que el circuito entero funciona sin depender de que el INE responda ni de esperar una ingesta larga.

$ docker compose -f docker-compose.dev.yml exec -T api \
      powergis seed --demo
Que no se te olvide Estos datos son inventados. Sirven para ver el sistema moverse, nunca para enseñar un informe a nadie. El propio comando te lo avisa en rojo.

Después: los municipios y el INE de verdad

La semilla del repositorio sólo llega a provincia —72 filas—. Sin los ~8.100 municipios, un estudio provincial no tiene con qué comparar y la ingesta del Padrón descarta cada fila sin dar ningún error.

$ docker compose -f docker-compose.dev.yml exec -T api \
      powergis load-municipios

# comprueba el mapeo ANTES de cargar: el INE renumera tablas
$ docker compose -f docker-compose.dev.yml exec -T api \
      powergis ine-verify
Deberías ver Algo por encima de 8.000 municipios cargados, y luego «Las 16 tablas del INE responden y mapean». Si ine-verify falla, te dice qué tabla y qué filtro, y con qué serie de ejemplo arreglarlo.
Esto necesita red Los municipios y el Padrón se descargan del INE. Si estás sin conexión, quédate en los datos sintéticos: el resto del tutorial funciona igual.

El circuito entero, sin navegador Etapa 4

Ésta es la etapa clave. Mete el payload real de [crear_proyecto_v6] por el mismo camino que recorrería desde el navegador, y va diciendo en voz alta qué pasa en cada tramo.

Por qué sin navegador

Desde el navegador, tres fallos muy distintos se ven exactamente igual —«no se crea el proyecto»—: que el mapeo esté mal, que la ubicación no se resuelva a código INE, o que el motor no conteste. Este banco de pruebas los separa.

$ make probar-formulario

Usa scripts/payload-formulario.json, que es copia literal de lo que produce buildPayload() en el shortcode. Si el formulario cambia, actualizas ese fichero y la prueba vuelve a ser cierta.

Deberías ver En el tramo 4, una docena de campos en target. Ahí es donde se nota que el perfil de cliente viaja entero: son los que alimentan el Match %. Y al final, «Circuito completo» con el número de proyecto.
Si el tramo 3 falla Es lo más probable la primera vez, y no es un error tuyo: el formulario manda nombres de zona y el motor exige el código INE. Si dim_geo está vacío no hay contra qué resolver. Vuelve a la etapa 3.

Ahora sí, desde el navegador Etapa 5

Con el circuito ya verificado, lo que pruebas aquí es la experiencia: el formulario, el informe y la subida a avanzado.

Crear un proyecto como cliente

  1. Entra en http://localhost:8080 como cliente/cliente. Hazlo con este usuario y no con admin: es el que tiene los permisos de verdad, y así compruebas de paso que el control de propiedad funciona.
  2. Ve a /nuevo-proyecto/ y rellena el formulario.
  3. Envía. Deberías aterrizar en el informe, que se pinta solo cuando el cálculo termina.
Ojo con el formulario en local El entorno local trae el shortcode del plugin ([powergis_form]), no el [crear_proyecto_v6] de tu tema, que aquí no está instalado. Para probar el formulario real, monta tu tema en el WordPress de pruebas añadiendo un volumen en docker-compose.dev.yml. El contrato ya está verificado en la etapa 4, así que esto es sobre todo probar el diseño.

El informe básico y la compra desde dentro

En el informe básico verás la demografía completa y, en el lugar de cada sección de pago, el índice de lo que contiene con los valores tapados. Los ••• no son un truco de CSS: el navegador nunca ha recibido esas cifras. Abajo del todo, un solo panel de compra.

Compruébalo tú mismo Abre las herramientas de desarrollo, pestaña Red, y mira la respuesta de /saas/v1/projects/…/report. Las secciones bloqueadas traen preview con etiquetas y ni un solo número.

Simular el pago

En local no hace falta Stripe: POWERGIS_DEV_MODE activa un simulador que dispara el mismo camino que dispararía el webhook.

Deberías ver La página se amplía sola, sin recargar a mano, y las secciones bloqueadas se rellenan. En la base de datos quedan la v1 y la v2 del mismo proyecto, y la v2 reutiliza la demografía en vez de recalcularla.
Nunca en producción POWERGIS_DEV_MODE desbloquea informes de pago sin pagar. No debe estar definido en powergis.es bajo ningún concepto.

El choque entre el plugin y tu tema Etapa 6

Esto no se nota en local, porque el tema no está. Se nota en powergis.es, y se nota mal: sin error, sin aviso, funcionando a medias.

Qué pasa exactamente

Tu tema registra saas/v1/projects/create en rest-projects.php. El plugin registra la misma ruta. WordPress no se queja: apila los dos manejadores y despacha el primero que coincida en método. Gana el que se registró antes —el plugin, porque los plugins cargan antes que el tema— y el del tema queda como código muerto que sigue pareciendo activo.

Lo mismo con el CPT project: tu tema lo registra en init con prioridad 0, el plugin en la 10, y register_post_type sobrescribe. Gana el plugin, con otros capability_type, otro rewrite y otro show_in_rest.

El problema no es cuál gana Es que gane por accidente. Un cambio de prioridad o de orden de carga invierte el resultado sin que nadie toque una línea de lógica.

Detectarlo

$ make dev-rutas
Deberías ver Una línea por ruta de saas/v1 con el número de manejadores. Cualquier ruta con más de uno sale marcada ⚠ CHOQUE. En powergis.es, el mismo wp eval con tu WP-CLI.

Resolverlo: que el ganador sea una decisión

La forma más limpia es que el tema se aparte solo cuando el plugin esté presente. Un guardia al principio del rest_api_init de rest-projects.php:

add_action('rest_api_init', function () {

    // El plugin powergis-connector se encarga de saas/v1.
    // Sin esto los dos registran la misma ruta y gana el que
    // cargue antes, que es un accidente, no una decisión.
    if ( class_exists( '\PowerGIS\REST_Projects' ) ) {
        return;
    }

    // … el registro actual, intacto …
});

Y lo mismo en cpt-project.php:

function saas_register_project_cpt() {
    if ( class_exists( '\PowerGIS\CPT' ) ) {
        return;
    }
    // … register_post_type actual …
}

Es reversible: si desactivas el plugin, el tema vuelve a hacerse cargo solo. Y deja escrito en el código quién manda, que es lo que ahora no está.

Una decisión de producto que queda abierta Tu CPT usa publicly_queryable => false, así que no hay página pública del informe; el del plugin sí la sirve en /proyectos/{slug}/. Las dos posturas son defendibles, pero hay que elegir una a conciencia: de ella depende cómo llega el cliente a su informe.

Las constantes

En wp-config.php, por encima de /* That's all, stop editing! */. Nunca en la tabla options, nunca en git.

define( 'POWERGIS_ENGINE_URL',  'https://motor.powergis.es' );
define( 'POWERGIS_HMAC_SECRET', '…' );   // el mismo que en el motor
define( 'POWERGIS_STRIPE_SECRET',         'sk_test_…' );
define( 'POWERGIS_STRIPE_WEBHOOK_SECRET', 'whsec_…'  );
define( 'POWERGIS_STRIPE_PRICE_ID',       'price_…'  );
No copies POWERGIS_DEV_MODE Es la constante del simulador de pago. En la copia de pruebas puede estar; en producción, jamás.

El orden que evita sustos

  1. Sube el plugin y actívalo. Todavía no toques el tema.
  2. make dev-rutas (o el wp eval equivalente) para ver los choques que hay.
  3. Pon los guardias de la etapa 6 en el tema.
  4. Vuelve a mirar las rutas: ya no debe haber ninguna con dos manejadores.
  5. Crea un proyecto tuyo, de principio a fin, mirando los logs.
  6. Prueba el pago en modo test con una tarjeta de prueba, y reenvía el mismo evento desde Stripe para comprobar que la idempotencia lo ignora.
Cuando esto pase, la fase 3 está cerrada Un proyecto creado desde el formulario real, calculado por el motor con datos del INE, cobrado por Stripe y ampliado solo tras el webhook.

Los síntomas que vas a ver, y qué significan de verdad.
