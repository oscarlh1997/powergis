Cada bloque de comandos lleva una etiqueta que dice dónde se ejecuta: azul para tu Windows, verde para el VPS. Es la confusión número uno en un despliegue, así que mírala antes de pegar nada.

Los pasos 1 a 4 no dependen del DNS. El 5 sí, y el 7 no puede hacerse sin él.

  1. 1

    La contraseña de root y tu clave SSH

    La pantalla «Secure your VPS access» te pide dos cosas, y las dos importan por motivos distintos.

    La contraseña: pulsa Generate

    Una contraseña tipo «VPSgis@54321» no aguanta

    Cumple las reglas del formulario, pero es exactamente la forma que prueban primero los diccionarios: palabra del proyecto, símbolo, secuencia numérica. Un VPS con IP pública empieza a recibir intentos de acceso por SSH a los pocos minutos de existir, y aquí el usuario es root.

    Usa el botón Generate del propio formulario y guarda el resultado en tu gestor de contraseñas. No hace falta que te la aprendas: en cuanto termines el paso 2 no se usa para entrar, sólo queda como respaldo para la consola web del panel.

    La clave: pégala en esa misma pantalla

    Donde dice «optionally add an SSH key». No es opcional para lo que vas a hacer — el script del paso 2 se niega a desactivar las contraseñas si no encuentra una clave instalada, precisamente para que no te quedes fuera.

    Si aún no tienes par de claves, créalo. Cuando pregunte por una frase de paso puedes dejarla vacía pulsando Enter.

    Tu Windows PowerShell
    ssh-keygen -t ed25519 -C powergis

    Ahora muestra la clave pública y cópiala entera:

    Tu Windows PowerShell
    Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
    Salida una sola línea
    ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... powergis

    Pega esa línea en el campo de la clave SSH. Si ya cerraste esa pantalla, el sitio equivalente es tu VPS → Clave SSH → Administrar → Añadir clave.

    La pública, nunca la privada

    Se sube id_ed25519.pub, con extensión .pub. El fichero sin extensión es la clave privada y no sale de tu máquina jamás.

    Listón

    ssh root@72.62.178.78 entra sin pedirte contraseña.

    Si te la pide, la clave no quedó instalada. Puedes entrar con la contraseña y seguir igualmente al paso 2 — el script te dirá que falta la clave y parará antes de desactivar nada, que es justo lo que tiene que hacer.

  2. 2

    Prepara la máquina

    Sube el script y ejecútalo. Deja usuario sin privilegios, SSH sólo por clave, cortafuegos, swap, Docker y el reloj sincronizado.

    Tu Windows PowerShell
    cd C:\Users\oscar\Downloads\powergis-backend\powergis
scp infra\hostinger\preparar-vps.sh root@72.62.178.78:/root/
ssh root@72.62.178.78
    En el VPS como root
    # tu usuario administrador se llama oscar, no el que asume por defecto
USUARIO=oscar bash /root/preparar-vps.sh

    Tarda un par de minutos. Verás secciones con ok en verde. Dos merecen atención:

    Salida lo que importa
    == Docker
   ok  instalado con el script oficial
       (o bien: "el script oficial no soportó esta versión
        de Ubuntu; voy por el repositorio" — también vale)

== SSH
   ok  1 clave(s) instaladas · root y contraseñas desactivados
    Ubuntu 26.04 es reciente

    El instalador oficial de Docker tarda meses en reconocer cada versión nueva de Ubuntu. Si aborta, el script instala desde el repositorio de Docker y, si tampoco existe carpeta para esta versión, usa la del LTS anterior. Los paquetes son los mismos; lo que falta es la carpeta, no el software.

    No cierres esta ventana todavía

    El script acaba de desactivar el acceso por contraseña. Si algo salió mal con la clave, esta sesión es tu única forma de arreglarlo — y la consola web de Hostinger, la segunda.

    Listón

    La línea de SSH dice root y contraseñas desactivados.

    Si en su lugar sale NO voy a desactivar las contraseñas, es que no encontró ninguna clave. No es un fallo: es el seguro para que no te quedes fuera. Todo lo demás —cortafuegos, swap, Docker, reloj— sí quedó hecho; instala la clave y vuelve a lanzar el script, que es idempotente.

  3. 3

    Comprueba lo que hizo, desde otra ventana

    Abre una segunda ventana de PowerShell, sin cerrar la primera.

    Tu Windows ventana nueva
    ssh oscar@72.62.178.78
    En el VPS como oscar
    sshd -T | grep -E 'permitrootlogin|passwordauthentication'
ufw status
swapon --show
timedatectl
docker run --rm hello-world
    ComandoTiene que decir
    sshd -Tpermitrootlogin no y passwordauthentication no
    ufw statusStatus: active, con 22, 80 y 443. Nada más.
    swapon --showuna línea con 2G
    timedatectlSystem clock synchronized: yes
    docker runHello from Docker!

    Lo de sshd -T no es rutina: las imágenes de Ubuntu traen un 50-cloud-init.conf que gana sobre sshd_config, así que editar el fichero principal —lo que dice casi toda guía— deja la contraseña activada y la máquina parece endurecida sin estarlo. Ese comando es lo único que dice la verdad.

    Listón

    Las cinco comprobaciones en verde. Entonces sí puedes cerrar la primera ventana.

    Sube el código

    Tu Windows desde la raíz del repositorio

    Salida esperada
    == Empaquetando
   ok  0,97 MB

== Desplegando en ~/powergis
  .env: no existe todavia  ->  cp .env.example .env

    Empaqueta con tar, sube y descomprime. El .env nunca entra en el paquete, así que las veces siguientes descomprimir encima no se lleva por delante tus secretos.

    Por qué tar y no Compress-Archive

    Compress-Archive aplana las carpetas cuando se le pasa una lista de ficheros: engine/src/powergis/cli.py llegaría como cli.py suelto en la raíz y no arrancaría nada. El script comprueba que las rutas están dentro antes de subir, y se niega si no.

    Listón

    Las tres líneas de «Empaquetando» en verde, y la lista de la raíz mostrando docker-compose.yml, engine, infra, Makefile.

  5. 5

    El registro DNS

    En hPanel, Dominios → powergis.es → DNS. No es la sección del VPS: es la del dominio.

    CampoValor
    TipoA
    Nombremotor — sólo eso
    Apunta a72.62.178.78
    TTL300

    Pulsa Añadir registro y comprueba que aparece en la tabla de abajo, junto a tus MX. Esa es la confirmación real; si no está ahí, no se guardó.

    Tu Windows saltándote la caché local
    ipconfig /flushdns
Resolve-DnsName motor.powergis.es -Server 1.1.1.1 -Type A
    Sólo el A. Nada de AAAA

    Si existe un registro AAAA, Let's Encrypt lo prefiere para el desafío, y Docker no enruta IPv6 salvo que lo configures. El certificado no se emitiría y el error hablaría de tiempos de espera sin mencionar IPv6 ni una vez.

    Listón

    Devuelve 72.62.178.78. No pases al paso 7 hasta que esto sea cierto: si Traefik pide el certificado antes, el desafío falla y Let's Encrypt limita los reintentos por dominio durante un rato largo.

    La configuración y los secretos

    En el VPS como oscar

# genera cada uno y cópialos a mano al .env
openssl rand -hex 32     # HMAC_SECRET
openssl rand -hex 32     # INTERNAL_API_KEY
openssl rand -hex 24     # POSTGRES_PASSWORD

nano .env
    VariableValor
    ENVproduction
    DEBUGfalse
    ENGINE_HOSTmotor.powergis.es
    ACME_EMAILtu correo
    POSTGRES_PASSWORDel de 24 bytes
    DATABASE_URLcon esa misma contraseña dentro
    HMAC_SECRETel primero de 32
    INTERNAL_API_KEYel segundo de 32
    ALLOWED_ORIGINShttps://powergis.es,https://www.powergis.es

    En nano: escribes, y luego Ctrl+O, Enter, Ctrl+X.

    El que se olvida siempre

    DATABASE_URL lleva la contraseña embebida en la propia URL. Cambiar POSTGRES_PASSWORD y no cambiarla ahí da un error de autenticación que parece de PostgreSQL y es de copiar y pegar.

    El secreto viejo está quemado

    guachineatata2026kimbapaquesuene ha circulado por el repositorio y por nuestras conversaciones. Quien lo tenga puede firmar peticiones válidas y generar informes a tu costa. No lo reutilices en ningún sitio.

    Listón

    make check-config pasa sin avisos. Valida el .env sin levantar nada, así que arregla aquí lo que se queje: el mismo error con el stack en marcha cuesta el triple de encontrar.

  7. 7

    Levanta el motor

    En el VPS como oscar
    make up
make ps

    La primera vez tarda varios minutos: construye la imagen del motor. El KVM 2 es el perfil por defecto, así que make up a secas — sin TIER.

    En el VPS comprobaciones
    curl -i https://motor.powergis.es/health              # 200
curl -i https://motor.powergis.es/internal/coverage   # 403
curl -i https://motor.powergis.es/ready               # 503, y está bien
    RespuestaQué significa
    /health → 200El motor vive y el certificado es válido. Sin -k: si necesitas esa bandera, el certificado no se emitió.
    /internal → 403Traefik bloquea los endpoints de operación desde fuera. Si sale 401, ese bloqueo no se aplicó.
    /ready → 503Correcto ahora mismo. La base de datos aún no tiene tablas y el motor lo dice en vez de fingir que está listo.
    Listón

    Los tres códigos tal cual. Con eso, el motor está desplegado y accesible desde internet.

Qué viene después

Con el motor en pie, quedan tres bloques, y están en la guía de despliegue completa:

  • El almacén — make almacen, make ine-verify, make ingest-ine. Ahí /ready pasa a 200.
  • WordPress — subir el conector y poner POWERGIS_ENGINE_URL y el mismo HMAC_SECRET en wp-config.php.
  • Stripe — producto, webhook y las pruebas en modo test.

Para volver a subir código después de un cambio, el paso 4 otra vez y luego make up. No toca los volúmenes: la base de datos se queda como está.

Si algo sale distinto

SíntomaCausa más probableQué hacer
Permission denied (publickey) La clave no está en el servidor, o estás usando el usuario que no es Antes del paso 2 es root; después, oscar
El scp se queda colgado Tu red bloquea el puerto 22 Prueba desde otra red, o usa la consola web del panel
Contenedores reiniciando en bucle Configuración inválida: en producción el motor se niega a arrancar con secretos débiles o DEBUG make logs dice cuál. Luego make check-config
El certificado no se emite El DNS no resolvía cuando Traefik lo pidió Comprueba el paso 5 y mira make logs de traefik. Espera antes de reintentar
/health no responde desde fuera ufw, o el certificado sudo ufw status en el VPS; el firewall de Hostinger lo tienes a 0 reglas, así que no es él
make: command not found Falta make sudo apt-get install -y make. El script lo instala, así que si falta es que no llegó a terminar
docker: permission denied El grupo docker no se aplicó a tu sesión Sal y vuelve a entrar por SSH

Si nada encaja, make diagnostico vuelca el estado completo a un fichero y me lo puedes pasar entero.
